# PS17 Gap Fix Task List

## P0: Critical fixes

### TASK 01 — Unify PMC/SMC naming
**STATUS: DONE for product-facing copy. Route/component identifiers retain `smc` for backwards compatibility.**

**Issue:** Project uses both PMC and SMC terminology.

**Fix:**

* Search entire frontend/backend for `SMC`, `smc`, `PMC`.
* Standardize to **Pune Municipal Corporation (PMC)**.
* Update UI, notifications, API responses, seed data and documentation.

**Done when:** No incorrect SMC references remain.

---

### TASK 02 — Single source of truth for SLA
**STATUS: DONE. `settings/slaConfig` is now the shared persisted source for admin UI, ticket creation, cron monitoring, and public policy.**

**Issue:** SLA values shown in UI don't always match values used by the SLA engine.

**Fix:**

* Create one SLA configuration.
* Make dashboard/public SLA page read from it.
* Make `calculateSlaDeadlines()` use the same configuration.
* Remove hardcoded duplicate SLA tables.

**Done when:** Every ticket's displayed SLA exactly matches the engine.

---

### TASK 03 — Monitor Response SLA separately
**STATUS: DONE. Response and resolution windows are monitored independently with warnings and escalation.**

**Issue:** Resolution SLA is monitored, but response SLA needs independent monitoring.

**Fix:**
Implement:

```text
Response SLA
→ 50% warning
→ 80% warning
→ breach
→ L1 escalation
```

and separately:

```text
Resolution SLA
→ 80% warning
→ breach
→ L1/L2 escalation
```

**Done when:** An unacknowledged complaint can independently trigger escalation.

---

### TASK 04 — Make status transitions authoritative

**Issue:** Different modules/routes can modify complaint status, creating inconsistent workflows.

**Fix:**
Create one server-side status transition service:

```text
validateTransition()
→ permission check
→ required data check
→ update status
→ create event
→ notify relevant users
```

**Done when:** Every status change goes through the same workflow.

---

### TASK 05 — Fix escalation recipient logic
**STATUS: DONE. L1 resolves the department head and L2 resolves a municipal official/admin.**

**Issue:** L1/L2 escalation can use generic roles without consistently resolving the actual responsible person.

**Fix:**

```text
L1 → Department Head of assigned department
L2 → Municipal Official / Administration
```

Resolve the actual user before sending notification.

**Done when:** Every escalation has a clear recipient.

---

# P1: Workflow intelligence

### TASK 06 — Create shared `ComplaintContext`

**Issue:** Agents mostly pass isolated outputs instead of maintaining one evolving case context.

**Fix:**
Create a shared object containing:

```text
complaint
classification
routing
priority
duplicate
assignment
SLA
escalation
communication
audit
```

Each agent reads previous decisions and adds its own result.

**Done when:** All agents operate on the same case context.

---

### TASK 07 — Improve duplicate detection

**Issue:** Dedup currently relies too heavily on a small recent-report candidate set.

**Fix:**

```text
New complaint
→ same ward
→ nearby radius
→ active complaints
→ compatible category
→ text similarity
→ Dedup Agent
```

**Done when:** Old but nearby active incidents can also be detected.

---

### TASK 08 — Automatically link duplicate complaints

**Issue:** Duplicate detection exists, but duplicate complaints should become part of the existing master incident workflow.

**Fix:**

```text
Complaint A
→ Incident #100

Complaint B
→ Dedup
→ 91% similarity
→ link to Incident #100
→ don't create another field task
```

Citizen B should still receive status updates.

**Done when:** One physical issue can have multiple citizen reports but one operational task.

---

### TASK 09 — Add Risk Score to Priority Agent

**Issue:** Priority relies too much on individual keywords.

**Fix:**
Calculate:

```text
Severity
+ Public Safety
+ Location impact
+ Traffic impact
+ Duplicate density
+ Time sensitivity
+ Evidence
```

Output:

```text
Risk Score: 87/100
Priority: Critical
Reason: ...
```

**Done when:** Priority has a numerical, explainable reason.

---

### TASK 10 — Add Confidence Gate

**Issue:** Low-confidence AI decisions can automatically enter the workflow.

**Fix:**

```text
>= 85% → automatic workflow

65–84% → department verification

< 65% → manual review
```

Critical safety complaints can bypass normal routing and receive immediate handling.

**Done when:** AI knows when it should and shouldn't act automatically.

# P1: Multi-department capability

### TASK 11 — Add Coordination Agent

**Issue:** Current routing primarily chooses one department.

**Fix:**
Coordination Agent determines:

```text
Primary Department
Supporting Departments
Responsibilities
Dependencies
```

Example:

```text
Water Supply → stop leak
Engineering → repair road
Traffic → manage intersection
```

**Done when:** One incident can create coordinated tasks across departments.

---

### TASK 12 — Introduce department tasks

**Issue:** Multi-department incidents need separate actionable work items.

**Fix:**

```text
Incident #1042
│
├── Task → Water Supply
├── Task → Engineering
└── Task → Traffic
```

Each task has:

```text
owner
status
SLA
deadline
dependency
completion evidence
```

**Done when:** Departments work on their own tasks under one incident.

---

### TASK 13 — Dependency-aware resolution

**Issue:** Incident should not be resolved while required department tasks remain incomplete.

**Fix:**

```text
Task A complete
      ↓
Task B unlocked
      ↓
Task C complete
      ↓
Incident eligible for resolution
```

**Done when:** Resolution depends on required tasks, not just one status update.

# P1: Resolution verification

### TASK 14 — Add Evidence Verification Agent

**Issue:** Worker can submit completion evidence, but verification should be more intelligent.

**Fix:**

```text
Original complaint
+ before evidence
+ after evidence
+ expected repair
        ↓
Evidence Agent
        ↓
PASS / FAIL / NEED REVIEW
```

Output:

```text
Verification Score: 92%
Reason: ...
```

**Done when:** Evidence influences whether a complaint can be resolved.

---

### TASK 15 — Add rework workflow

**Issue:** Failed resolution should have an explicit workflow.

**Fix:**

```text
Worker completes
→ Evidence verification FAIL
→ Rework requested
→ Worker notified
→ Work again
→ Evidence submitted
```

**Done when:** Failed verification does not simply become `Resolved`.
